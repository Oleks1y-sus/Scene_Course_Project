# Відповідність вимогам курсового проєкту

Проєкт орієнтований на **12 балів** + бонусний функціонал. Нижче — зіставлення вимог із реалізацією.

## Рівень 12 балів (потрібно 2+, реалізовано 3)

1. **Розмежування прав доступу USER/ADMIN.** Перевіряється сервером (`requireAdmin`, `requireAuth`), а не лише приховуванням UI. Додатково: server-side layout `/admin`, заборона змінювати власну роль, захист останнього адміністратора.
2. **Повний CRUD другої сутності.** Користувачі: перегляд, створення адміністратора, редагування ролі/статусу, видалення (анонімізація + приховування заходів). Скарги: створення, перегляд, вирішення.
3. **Завершений сценарій.** Обране + реєстрація + демо-ефір: користувач знаходить захід → додає в обране → реєструється → власник запускає ефір → завершує → реєстрації стають «відвідані» → статистика оновлюється.

## Що підготувати до захисту

1. Посилання на Vercel, Render, Supabase (без секретів).
2. Демо-акаунти (або створіть тестові під час захисту).
3. Показати: реєстрацію → вхід → каталог → створення заходу → модерацію → скаргу → адмінпанель → тіньовий бан → видалення.
4. Показати мережу: клієнт звертається лише до `/api/v1`, не до БД.
5. Показати серверні перевірки: спробувати відкрити `/admin` під USER, відправити `<script>` у назві, перевищити ліміт.
6. Результати W3C HTML/CSS, PageSpeed, консоль браузера — у звіті.
